# Models (`R/`, `scripts/`)

The stochastic SEIR simulation (one grid row per array task) and the aggregation of all runs into
results.

## Key files & entry points

- `scripts/simulate.R` — entry for `02_simulate`: reads row `SLURM_ARRAY_TASK_ID` of the grid,
  loads that row's region, runs `simulate_seir()`, writes `runs/<row_id>.parquet`.
- `scripts/aggregate.R` — entry for `03_aggregate`: checks run count, calls `summarise_runs()`,
  writes tables and figures.
- `R/seir.R` — `simulate_seir(pop, params)`: discrete-time, network-based SEIR.
- `R/load_pop.R` — reads population parquet (`arrow`), validates the schema.
- `R/summarise.R` · `R/plots.R` — attack-rate / peak summaries by parameter; figures.
- `tests/testthat/` — unit tests with a 500-person fixture population.

## Parameter grid

`params/grid.csv`, generated by `params/make_grid.R` (committed): full factorial of `r0`,
`incubation_days`, `contact_scale` × region, 10 replicate `seed`s each ≈ 1 000 rows. Task id *i* ↔
row *i* (0-based); `row_id` is stable across grid regenerations for unchanged combinations.

## Aggregation

`03_aggregate` refuses to run unless `runs/` holds exactly one file per grid row (lists missing
`row_id`s otherwise). Output in `$SIM_RESULTS/<date>/`: `tables/attack_rate.csv`,
`tables/peak.csv`, `figures/*.pdf`, plus `grid.csv` and `sessionInfo.txt` for provenance.

## Gotchas

- `set.seed(row$seed)` must stay the first random call in `simulate.R` — adding randomness before
  it changes every result.
- `data.table` threads: `setDTthreads(as.integer(Sys.getenv("SLURM_CPUS_PER_TASK", 1)))`; without
  it data.table grabs every core on the node and gets throttled.
- Runs for `r0 > 4` take ~3× longer — see [jobs](jobs.md#resources) before widening the grid.
- Don't aggregate on the login node even "just to check" — use `salloc` ([recipes](../recipes.md#debug-one-task-interactively)).
